# SMW Bingo prototype

合言葉で集まる、最大4人のスーパーマリオワールド用ビンゴです。ルーム・参加情報・進捗はメモリ上だけに保存します。

## ディレクトリ構成

- `frontend/`：React・Vite、フロントの設定・テスト。
- `backend/`：Goモジュール、API、ルーム・カード生成、カタログ、Air設定。
- `docs/`：設計・開発手順・ゲーム調査資料。
- ルート：ワークスペースとDockerの共通設定。

`pnpm dev`・`pnpm build`・`pnpm test` はルートで実行できます。Goコマンドは `go -C backend ...`、または `backend/` 内で実行します。フロントのビルド先は `backend/static/`（Git管理外）で、Goが埋め込んで配信します。

## 起動

Go 1.25.4 以上、Node.js 24、pnpm 12.4.1を使用し、リポジトリのルートから実行します。pnpmのバージョンは `package.json` の `packageManager` で固定しています。フロントはReact＋TypeScriptです。

```sh
pnpm install --frozen-lockfile
pnpm build
go -C backend run .
```

ブラウザで http://localhost:8080 を開くと、アクティブなルーム一覧を表示します。「ルーム作成」ボタンからルーム名・合言葉を入力して作成できます。作成者は管理者となり、自動ではプレイヤーに参加しません。参加者は一覧の「ルームを開く」または招待URLから、表示名と合言葉を入力して参加します。入室するとすぐにカードをクリックして進捗を更新できます。開始操作やタイマーはありません。

一覧には参加受付中・満員・対戦中のルームを表示し、終了・削除されたルームは除外します。トップページを開いている間は1秒ごとに一覧を更新します。

フロントを編集するときは、Goサーバーを起動したまま別ターミナルで `pnpm dev` を実行し、http://127.0.0.1:5173 を開きます。ViteがHTTP APIとWebSocketをGoサーバーへ転送します。

Dockerではフロントのビルドも自動で行います。

```sh
docker build -t smw-bingo:prototype .
docker run --name smw-bingo -p 8080:8080 smw-bingo:prototype
```

| 環境変数 | 既定値 | 用途 |
| --- | --- | --- |
| `ADDR` | `:8080` | 待ち受けアドレス |
| `BINGO_DATA` | `backend/bingo.json` | お題データのパス |
| `SECURE_COOKIE` | `false` | HTTPSで公開する場合は `true` |

## ルール

- **Standard（既定）**: 同一プレイヤーが1ラインとクッパ撃破を両方達成すると勝利。達成順は問いません。
- **Line（派生）**: 1ラインで勝利。
- **Race**: 全員が同じカードを使い、各自でマスを達成します。
- **Lockout**: 各マスは先に達成した1人だけが取得できます。勝利確定前は本人が取り消せます。
- 定員はプレイヤー4人。管理のみの作成者は枠を使わず、進捗を閲覧して終了を操作できます。
- 作成者自身がプレイする場合は「プレイヤーとして参加」から表示名とカラーを登録します。終了前は参加を取り消せますが、管理権限は保持します。途中参加・退出も可能です。カード再生成は全員のマスとクッパ撃破の記録が空の場合だけ可能です。
- 作成者は終了前に他のプレイヤーをキックできます。対象者の参加セッション・進捗・マスの占有を解除します。終了後は結果を保持するためキックできません。キックは参加禁止ではないため、終了前で合言葉を知っていれば再参加できます。
- ゲーム終了・カード再生成・ルーム削除は主催者のみ。「ゲーム終了」で勝者なしで終了し、進捗更新を停止します。ルームは終了前でも削除できます。
- 一度勝者が決まったら進捗を固定します。再戦は新しいルームで行います。

## カード生成

お題を画面から調整する場合は `/admin` の管理者ページを使います。Discord認証と許可ユーザーIDの設定が必要です。設定方法は [管理者ページの設定](docs/DEVELOPMENT.md#管理者ページの設定) を参照してください。

`backend/bingo.json` に51件のお題を保持し、達成条件の確認が必要な11件を保留、40件を抽選対象としています。管理画面の保留理由を空にすると再有効化できます。元データの重複1件を統合し、`difficulty` を `timeMin`・`exec`・`risk`・`tags` に置き換えています。

お題の内容は `name`、ワールド名は `world`、コース名や種別は文字列の `level` に分けています。たとえば `{ "name": "通常ゴール", "world": "チョコレーとう", "level": "コース3" }` です。場所を指定しないお題は `world`・`level` とも空文字、ワールド全体のお題や番号のないコースは `level` を空文字にします。表記は [LEVEL_LIST.md](docs/LEVEL_LIST.md) に合わせ、画面では3つを組み合わせて表示します。

`timeMin` は、ゲーム開始からそのお題を単独で達成するまでに最低限必要な分数です。ステージへの到達、コースの解放、必要なアイテムなどの準備、お題自体の達成をすべて含めます。失敗によるやり直しは `risk` で補正するため、この値には含めません。分未満は切り上げて整数で登録します。たとえば到達・準備が8分、達成に2分かかるお題なら `timeMin: 10` です（説明用の数値）。場所指定のないお題も同じ基準で設定します。

**既存51件の所要時間・操作精度・リスク・タグはプロトタイプ用の暫定値です。到達・準備時間を含む所要時間への校正は未実施です。** 実測値に基づく時間の更新は管理者ページまたはデータファイルで行ってください。70〜100件への増量は推奨事項であり、この版では既存のお題を維持しています。

- コスト: `timeMin × (1 + 0.3 × (risk - 1))`
- ラインの評価時間: `お題5個のコスト合計 − Σ((その区間を使うお題数 − 1) × 区間の基準時間)`。使われている区間ごとに重複分を差し引きます。リスク補正の加算分はお題ごとに維持します。
- 25マスを選択し、中央→対角線→その他の順に配置します。
- 横5列・縦5列・斜め2列の全12ラインで、空文字以外の同じ `world` を2個以上配置しません。コース番号が異なっても同じワールドなら重複です。配置できない組み合わせを引いた場合は25件を再抽選します。
- 同一ラインの地域タグ重複は重み2、種類タグ重複は重み1。時間の偏差は補正後の全12ラインの平均絶対偏差です。未配置マスは選択済み25件の平均コストで補完して評価します。
- 12ラインの最短合計に、Standardのみクッパまでの固定所要時間を加算します。この値が目標範囲内の場合だけ採用します。
- 画面の時間設定は「レース全体の目標上限」の1項目だけです（既定90分）。Standardではビンゴ完成とクッパ撃破までを含み、Lineではビンゴ完成までを指します。下限は設けません。
- クッパ経路が未登録の場合、推定計算ではStandardの通常ルート分として暫定15分を上限の内側に含めます。これは内部の見積もり用の値で、利用者が別途指定する終了時間ではありません。Lineでは加算しません。
- **目標上限はカード生成の目安であり、試合の強制終了時刻ではありません。**
- 同じデータ・シード・生成条件なら同じカードになります。空シードはUUIDを発行し、表示されたシードで再現できます。
- 探索は最大256回です。時間範囲やワールド構成によっては探索に失敗します。その場合は重複したカードを返さずエラーにするため、シード・お題のワールド構成・時間範囲を見直してください。

### 経由区間

管理者ページの「全区間の基準時間」に、あらかじめ定義した経由区間を固定一覧で表示します。未設定の時間は空欄で表示し、お題・クッパ経路が参照する区間だけ入力して保存できます。各お題では「経由区間」のドロップダウンから通る区間を追加します。同じ区間の重複追加はできません。「外す」で取り消せます。

バニラドーム周辺は、次の4区間を独立して設定します。

| ID | 区間 |
| --- | --- |
| `vanilla:common` | バニラ1の分岐前まで（出口攻略・再入場は別計上） |
| `vanilla:cheese` | コース1終了後からチーズブリッジへ（コース1は含めない） |
| `vanilla:plateau` | コース1終了後からバニラだいちへ（コース1は含めない） |
| `plateau:butter` | バニラだいちからバターブリッジへ |

チーズブリッジ方面のお題には共通区間とチーズ方面の区間を、バターブリッジ方面のお題には共通区間・バニラだいち方面・バターブリッジへの区間を指定します。両方を回るお題では両方の分岐を指定できます。異なる分岐同士は重複として差し引かず、同じIDの区間だけを補正します。対象の `world` や配置用の `tags` とは別の情報です。

区間一覧と表示名は `backend/bingo/route_segments.json` にまとめています。他の経路も分割する場合は、互いに重ならない区間のIDと表示名をここに定義して再ビルドします。分割前のエリアIDは `retiredAreas` に移し、元の時間を新しい区間へ自動配分しません。

既存データとの互換性のため、JSONのプロパティ名は `routeAreaTimes`（区間ID→整数の分数）と `routeAreas`（お題が通る区間IDの配列）を維持しています。基準時間は**その区間だけを通過する時間**です。同じIDは同じ道中を指します。基準時間は1〜1440分の整数で、お題が通る区間の合計は `timeMin` 以下にします。

旧「バニラドーム」「バニラだいち」の時間は参考値として保持し、計算の重複補正には使いません。新しい4区間の時間は管理者が設定してください。お題に残る旧エリアの指定は「要再設定」と表示し、通る区間を選び直してから保存します。元の `backend/bingo.json` の時間・お題・経路を自動で書き換えることはありません。

例として、5個のお題がそれぞれ10分・リスク1で、同じ8分区間を使うなら、見積もりは `50 − 4 × 8 = 18分` です。作業自体の同時達成は補正しません。管理画面の「クッパへの経路」に実測値を登録すると、ラインと経路の共有解放区間も1回分だけ計上します。未登録の場合は暫定15分の固定加算です。設定を更新しても、作成済みカードには生成時の基準時間が保持されます。
## 参加セッション

進捗はWebSocketで変更直後と1秒ごとに同期します。切断中は1秒間隔のHTTP取得に切り替え、自動でWebSocketに再接続します。接続中はHTTPポーリングを止めます。HTTPSで利用する場合は `wss://` に接続します。

Discord連携はありません。合言葉の照合後にルーム専用のHttpOnly Cookieを発行します。期限は24時間です。進捗更新のプレイヤーIDはCookieから決定し、リクエスト側から他のプレイヤーを指定できません。

同じブラウザで同じ招待URLを開くと復帰できます。複数人で確認する場合は別ブラウザ・別プロファイル・別端末を使ってください。Cookieを失った場合の参加枠の復旧や主催者の引き継ぎはありません。終了前の参加者は退出できます。セッションを失った参加者の枠は主催者がキックして空けられますが、再参加時に以前の進捗は復元されません。

ルーム作成・参加試行・単独カード生成は、接続元IP単位で合計20回/分に制限しています。リバースプロキシ経由ではプロキシのIP単位になります。

サーバーの再起動でルームとセッションはすべて失われます。これは少人数で試すためのプロトタイプです。HTTPS公開時は `SECURE_COOKIE=true` に設定してください。

## 検証

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm test
pnpm format:check
go -C backend test -race -cover ./...
go -C backend vet ./...
```

ブラウザの結合テストは `frontend/tests/browser.mjs` と `frontend/tests/admin-browser.mjs` です。別途サーバーを起動し、Playwrightが利用できる環境で実行します。

```sh
mkdir -p tmp/browser-tools
pnpm --dir tmp/browser-tools --ignore-workspace add playwright
pnpm --dir tmp/browser-tools --ignore-workspace exec playwright install chromium
PLAYWRIGHT_MODULE="$(pwd)/tmp/browser-tools/node_modules/playwright/index.mjs" pnpm test:browser
```

PowerShellでは `$env:PLAYWRIGHT_MODULE = (Resolve-Path './tmp/browser-tools/node_modules/playwright/index.mjs').Path` のように環境変数を設定します。`BINGO_URL` で接続先（既定 `http://127.0.0.1:8080`）、`BROWSER_EXECUTABLE` でブラウザ実行ファイルを指定できます。ブラウザテストは使い捨てのテストルームを作成します。

APIの詳細は [DEVELOPMENT.md](docs/DEVELOPMENT.md) を参照してください。

NodeCGなどの外部表示向けに、参加枠を使わない読み取り専用の観戦APIがあります。ルームIDだけで、誰でもHTTPまたはWebSocketからカード・全員の進捗・勝敗を取得できます。認証は不要です。接続方法は [観戦APIとNodeCG連携](docs/spectator-api.md) を参照してください。


GAME_NOTE.mdに基づく改善の詳細と実測待ちの項目は [分布設計](docs/bingo-distribution.md) を参照してください。同じラインから類似・包含課題を除くには、管理画面で同じ「配置禁止グループ」を指定します。
